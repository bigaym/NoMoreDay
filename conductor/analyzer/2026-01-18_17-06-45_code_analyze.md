# Code Risk Analysis Report: Magic Numbers & Constant Management

**Date:** 2026-01-18
**Analyst:** Code Risk Analyzer (Agent)
**Scope:** `src/game`, `src/systems`, `src/states`

## 1. Executive Summary
A deep scan of the codebase revealed **over 2,700 instances of magic numbers** (unnamed numeric literals) scattered across logic, rendering, and UI systems. While some are harmless (e.g., offsets), many represent critical "source of truth" duplications that pose maintenance risks and potential logical inconsistencies.

## 2. Critical Risks & Technical Debt

### 2.1. Logic/Physics Consistency Risks
*   **Duplicate Cap Enforcement**: 
    *   `src/game/components/Common.hpp` defines `Cap::CDR = 0.75f`.
    *   `src/states/GameplayState.cpp` (L485) hardcodes `if (cdr > 0.75f) cdr = 0.75f;`.
    *   *Risk:* Changing the cap in `Common.hpp` will not update `GameplayState.cpp`, leading to desync between intended design and actual gameplay.
*   **Inconsistent Physics Thresholds**:
    *   Velocity epsilon checks vary between `0.001f` (GameplayState) and `0.01f` (AISystem). This can cause jitter or "stuck" entities that are considered moving by one system but stopped by another.

### 2.2. Rendering/Logic Coupling
*   **Hardcoded UI Colors**: 
    *   Files like `UISystem.cpp`, `UIInventory.cpp`, and `UICharacter.cpp` contain hundreds of `Color{r,g,b,a}` definitions.
    *   *Risk:* Theming changes require hunting down hundreds of lines across C++ logic files.
    *   *Violation:* Visual constants are not in `src/engine/render/GPUData.hpp` as required.
*   **Particle System Limits**:
    *   Loops like `for (int i = 0; i < 15; ++i)` for particle emission are hardcoded in `EffectSystem.cpp`.
    *   *Risk:* Cannot easily scale graphics quality (Low/Med/High) without recompiling code.

## 3. Performance Bottlenecks (Inferred)
*   **Redundant Random Generation**:
    *   High frequency of `GetRandomValue` and `rand()` calls inside update loops (e.g., `EffectSystem.cpp`).
    *   *Suggestion:* Batch random number generation or use a pre-computed sequence for visual-only effects.

## 4. Refactoring Suggestions

### 4.1. Rendering Constants -> `src/engine/render/GPUData.hpp`
**Action:** Move all UI and VFX color definitions to `NoMoreDay::components::Colors`.

*   **Source:** `src/systems/ui/*.cpp`, `src/states/*.cpp`
*   **Target:** `src/engine/render/GPUData.hpp`
*   **Example Changes:**
    ```cpp
    // Current (Bad)
    DrawText(..., Color{255, 215, 0, 255}); 
    
    // Target (Good)
    DrawText(..., Colors::UI_GOLD);
    ```

### 4.2. Game Logic Constants -> `src/game/components/Common.hpp`
**Action:** Centralize combat, physics, and AI thresholds.

*   **Source:** `src/systems/combat/CombatSystem.cpp`, `src/states/GameplayState.cpp`
*   **Target:** `src/game/components/Common.hpp`
*   **Key Candidates:**
    *   `GameplayState.cpp`: `0.75f` (CDR Cap) -> `Cap::CDR`
    *   `CombatSystem.cpp`: `1.5f` (Default Crit Damage) -> `Combat::DEFAULT_CRIT_DAMAGE`
    *   `Physics`: Epsilon values (`0.001f`) -> `Physics::EPSILON`

### 4.3. Priority Fixes
1.  **GameplayState.cpp**: Replace hardcoded `0.75f` CDR cap with `Cap::CDR`.
2.  **CombatSystem.cpp**: Replace magic numbers in damage formulas with `Combat::Pipeline` constants.
3.  **UI Systems**: Abstract common colors (Rarity, Health, Mana) into `GPUData.hpp`.

## 5. Conclusion
The codebase has high "magic number" density. Immediate refactoring should focus on **logic caps** (CDR, Res) to prevent gameplay bugs. Secondary focus should be on **UI theming** to decouple visuals from C++ logic.
