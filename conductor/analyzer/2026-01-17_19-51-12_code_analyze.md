# Code Risk Analysis Report
Date: 2026-01-17 19:55:00

## Summary
The codebase is generally safe from raw pointer abuse, but suffers from significant **allocation-based performance risks** that jeopardize the 10,000 entity target. Critical issues include unlimited memory growth in the stats cache, per-frame vector allocations in core loops, and a logic/performance conflict in the Sword Intent system.

## Critical Risks (High Priority)
### 1. Memory Leak in Stats Cache (`StatsSystem::s_tagStatCache`)
- **Description**: `s_tagStatCache` stores cached stat values keyed by Entity ID. `ClearCache` is only called during `Recalculate`. There is no evidence that `ClearCache` is called when an entity is destroyed.
- **Consequence**: Memory usage will grow indefinitely as enemies spawn and die, eventually causing OOM (Out Of Memory) or cache locality degradation.
- **Recommendation**: Register a destruction signal handler in `Registry` or call `StatsSystem::ClearCache(entity)` in `EnemySpawnSystem`/`CombatSystem` upon death.

### 2. Allocation Hotspot in Skill Loop (`SkillSystem.cpp:796`)
- **Description**: `std::vector<entt::entity> entities(view.begin(), view.end());` effectively copies the entire active skill list every single frame to avoid iterator invalidation.
- **Consequence**: At 10,000 entities, this is a massive periodic allocation/free cycle (e.g., 20k-40k items active), causing stuttering (GC-like pauses).
- **Recommendation**: Use a `static` or `thread_local` vector that is `reserved` to max capacity and `cleared` each frame, reuse memory instead of reallocating.

### 3. Logic/Performance Trap: Sword Intent & Recalculate
- **Description**: `SwordIntent` stacks are updated in `SkillSystem` but do **not** trigger `StatsDirty`. Thus, the `AttackSpeed` bonus from existing stacks is stale/inert until something else dirties the stats. fixing this requires triggering `Recalculate` on stack change, but `StatsSystem::Recalculate` is currently too heavy (allocates `std::unordered_map` and parses strings).
- **Consequence**: Currently: Gameplay mechanics are broken (stale stats). If Fixed: Performance tanks due to heavy allocations inside `Recalculate` running frequently.
- **Recommendation**: First, optimize `StatsSystem::Recalculate` to remove string maps and allocations. Then, correctly tag `StatsDirty` when stacks change.

## Performance Bottlenecks
- **StatsSystem String Parsing**: `Recalculate` uses `std::unordered_map<std::string, ...>` for Set Bonuses AND parses strings like `IntToCritMult:` inside the loop. This is extremely slow for a hot path.
- **RenderSystem Debug Allocation**: `DownloadFlowField` creates a `std::vector` copy every frame when debug draw is active.

## Refactoring Suggestions
1. **Data Optimization**: Convert all String-based IDs (Sets, Affixes) to `uint32_t` hashes or Enums to enable zero-allocation lookups in `StatsSystem`.
2. **Cache Management**: Implement RAII-style cleanup for Entity stats cache.
3. **Loop Optimization**: Replace per-frame vector copies in `SkillSystem` with reusable scratch buffers.
