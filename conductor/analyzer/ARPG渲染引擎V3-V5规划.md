# 高性能2D ARPG渲染引擎架构演进报告：V3设计与V4/V5长期规划

## 1. 执行摘要

在当前动作角色扮演游戏（ARPG）的竞争格局中，以《流放之路2》（Path of Exile 2, PoE2）和《暗黑破坏神IV》（Diablo IV, D4）为代表的顶级作品，已经将玩家对画面表现和流畅度的期望提升到了前所未有的高度。这些游戏不仅在视觉上实现了从传统2D/2.5D向全3D物理渲染（PBR）的跨越，更在技术底层通过GPU驱动（GPU-Driven）的架构变革，支撑起了同屏数千个独立计算单位（Entities）的高强度战斗场景。

本报告基于现有的V2源代码分析与V3设计文档，针对当前引擎存在的CPU瓶颈——特别是地图战利品（Loot）渲染与大量文字（Damage Text/UI）渲染的热路径——提出了全面的架构重构方案。报告详细阐述了V3阶段如何通过计算着色器（Compute Shader）与间接绘制（Multi-Draw Indirect, MDI）技术实现“零CPU负载”的渲染管线；V4阶段如何引入针对2D精灵（Sprite）的PBR材质系统与集群前向渲染（Clustered Forward+）；以及V5阶段如何落地基于辐射级联（Radiance Cascades）的实时全局光照技术。

核心结论指出，传统的“CPU提交-GPU绘制”模式已无法满足现代ARPG对海量同屏单位的需求。唯有将场景管理、粒子模拟、文字排版及遮挡剔除等逻辑完全下放至GPU，才能释放CPU算力用于更复杂的Gameplay逻辑，从而在保持144Hz以上高帧率的同时，实现次世代的视觉效果。

------

## 2. 现状分析：V2架构的瓶颈与局限性

在深入规划V3之前，必须对现有V2引擎的性能瓶颈进行外科手术式的解剖。基于代码库的静态分析与运行时性能特征（Profiling）推断，V2引擎在处理高密度场景时表现出的帧率骤降，其根源在于CPU与GPU之间的交互模式过于陈旧。

### 2.1 传统渲染管线的CPU开销

V2引擎采用的是经典的“立即模式”或“排序后批量提交”模式。在每一帧中，CPU必须执行以下操作：

1. **遍历场景图（Scene Graph Traversal）：** 检查每一个游戏对象（GameObject）的可见性。
2. **状态排序（State Sorting）：** 为了减少渲染状态切换（Draw Call Batching），CPU需要根据材质、纹理ID对渲染队列进行排序。
3. **顶点生成（Vertex Generation）：** 对于文字和动态精灵，CPU每一帧都在重新计算顶点位置（例如伤害数字的飘动轨迹），并将其拷贝到动态顶点缓冲区（Dynamic Vertex Buffer）。
4. **绘制调用（Draw Call Submission）：** 最终通过图形API（如OpenGL/DX11）发起绘制命令。

在ARPG的典型战斗场景中，屏幕上可能同时存在50只怪物、数百个飞行投射物、数十个地面战利品以及每一击产生的一串伤害数字。这导致每帧的Draw Call数量激增，或者在尝试合批（Batching）时消耗大量的CPU周期进行内存拷贝。

### 2.2 “热路径”瓶颈：战利品与文字渲染

根据分析，V2引擎在以下两个特定路径上存在严重的性能断层：

#### 2.2.1 地图战利品（Loot）

ARPG的战利品通常具有“海量”和“堆叠”的特性。当一场战斗结束后，地面上可能散落数百件物品。

- **V2痛点：** 每一个战利品通常包含一个3D模型（或2D图标）、一个光柱特效、以及一个包含物品名称、稀有度颜色的UI标签。在V2中，这些元素往往被视为独立的对象进行更新和渲染。标签的布局计算（防止重叠）通常在CPU上通过简单的包围盒碰撞检测完成，这是一个$O(N^2)$复杂度的算法。当物品数量超过100时，仅标签避让逻辑就能占满单帧的CPU预算（>16ms），导致游戏逻辑线程卡死。

#### 2.2.2 动态文字（Damage Numbers & UI）

伤害数字是ARPG中最频繁产生的视觉元素。

- **V2痛点：** 现有的文字渲染依赖于CPU排版。每一帧，CPU都要遍历所有存活的伤害数字字符串，查询字体图集（Font Atlas）的UV坐标，计算字偶间距（Kerning），生成四个顶点，并处理缩放和透明度动画。这种每一帧都在重建网格（Mesh Rebuilding）的做法，在大量暴击触发时（瞬间产生几十个数字），会造成巨大的内存带宽压力和CPU缓存未命中（Cache Miss）。

## 3. V3架构设计：全面转向GPU驱动（GPU-Driven）

V3设计的核心目标是**“去CPU化”**。我们将彻底改变数据流向，不再让CPU告诉GPU“画什么、在哪里画”，而是让CPU只负责同步“发生了什么”（例如：造成了100点伤害），由GPU全权负责“怎么画、画在哪里、如何运动”。

### 3.1 核心技术基石

为了支撑V3架构，我们需要引入现代图形API（Vulkan/DX12/Metal）的核心特性，即便是在DX11/OpenGL环境下，也应尽可能模拟这些行为。

| **技术特性** | **V2 (现状)**                    | **V3 (目标)**                            | **优势解析**                           |
| ------------ | -------------------------------- | ---------------------------------------- | -------------------------------------- |
| **数据传输** | 每帧上传顶点数据 (Dynamic VBO)   | 持久化结构缓冲区 (SSBO/StructuredBuffer) | 消除PCIe带宽瓶颈，数据常驻显存         |
| **绘制指令** | `DrawIndexed` (CPU循环调用)      | `Multi-Draw Indirect` (MDI)              | 单次API调用绘制数万物体，GPU生成指令   |
| **资源绑定** | 频繁切换纹理槽位 (Texture Units) | 无绑定资源 (Bindless) / 纹理数组         | 消除状态切换开销，Shader可访问所有纹理 |
| **逻辑处理** | CPU计算动画/物理                 | Compute Shader (CS) 并行计算             | 利用GPU万核并发处理海量粒子/文字       |

### 3.2 GPU驱动的文字渲染系统（Text Rendering）

针对文字渲染的热路径优化，V3将实现一套完全基于GPU的排版与绘制流水线。这不仅是为了性能，也是为了实现无损的高清字体渲染。

#### 3.2.1 基于SDF/MSDF的字体图集

传统的位图字体（Bitmap Font）在缩放时会模糊或像素化。为了对标D4和PoE2的高清UI，我们将采用**多通道有向距离场（Multi-Channel Signed Distance Field, MSDF）**技术 。

- **原理：** MSDF在纹理的RGB通道中存储到字形边缘的距离信息。Shader通过插值计算距离，可以完美重建矢量边缘。
- **优势：** 单张4K贴图即可容纳所有常用汉字与符号，且支持无限放大保持锐利，非常适合ARPG中忽大忽小的暴击数字。

#### 3.2.2 计算着色器排版（Compute Shader Typesetting）

我们将摒弃FreeType在运行时的CPU介入。

1. **字形数据缓冲区（Glyph Info Buffer）：** 在初始化阶段，将所有字符的度量信息（Metrics：宽、高、X偏移、Y偏移、进给量Advance）上传至一个只读SSBO。
2. **实例数据流：** CPU仅需向GPU发送一条精简指令：“在坐标(X,Y)显示字符串ID=1024，数值=9999”。
3. **排版核心（Layout Kernel）：** 一个Compute Shader被分派（Dispatch）。
   - **并行前缀和（Parallel Prefix Sum）：** 针对长字符串，利用并行算法计算每个字符的屏幕X坐标偏移。
   - **顶点生成：** 每个线程处理一个字符，根据Glyph Info生成对应的Quad数据（位置、UV、颜色），写入到全局的`RenderBuffer`中。
   - **间接参数更新：** 原子操作（Atomic Add）更新`IndirectDrawArgs`缓冲区中的实例数量。

通过这种方式，成千上万个伤害数字的生成、排版、动画（飘字、重力下落、淡出）全部在GPU上完成，CPU消耗几乎为零 。

### 3.3 高性能战利品渲染与GPU物理避让

针对地图战利品堆叠的问题，V3将引入基于GPU的力导向图布局（Force-Directed Layout）算法来处理标签避让。

#### 3.3.1 间接绘制与自动合批

所有地面掉落物共享同一个Shader和Mesh（或是通过Geometry Shader生成的Quad）。

- **数据结构：** `LootInstance`结构体包含物品ID、世界坐标、稀有度颜色等。
- **MDI流程：**
  1. CPU将新增掉落物写入`LootBuffer`。
  2. **剔除Shader（Cull CS）：** 每一帧，Compute Shader遍历`LootBuffer`，判断物品是否在视锥体（Frustum）内。
  3. **可见性列表：** 通过视锥测试的物品索引被写入`VisibleIndexBuffer`。
  4. **渲染：** 执行`glMultiDrawElementsIndirect`，仅绘制可见物品。

#### 3.3.2 标签避让的GPU实现

为了解决标签重叠，我们不再使用CPU进行矩形碰撞检测，而是利用GPU的网格算力。

- **算法描述：**
  1. 将屏幕划分为较粗的网格（例如32x32像素为一个Cell）。
  2. **迭代1（散列）：** Compute Shader将每个可见标签的中心点映射到网格中。
  3. **迭代2（斥力计算）：** 每个标签检查自身所在的网格及周边网格。如果存在其他标签，计算一个排斥力向量（Repulsion Vector）。
  4. **迭代3（位置更新）：** 根据斥力向量更新标签的渲染坐标（注意：不修改逻辑坐标，仅修改显示的偏移量）。
- **效果：** 这是一个在GPU上运行的简易物理模拟。经过2-3帧的迭代，堆叠在一起的标签会自动“弹开”，形成整齐排列的布局，且过程极其流畅，完全不占用CPU 。

## 4. V4架构规划：2D PBR材质与集群前向渲染

解决了性能问题后，V4的重点转向画质，目标是实现“虽然是2D贴图，但光影如同3D建模”的视觉欺骗效果。

### 4.1 2D PBR材质标准（Material Standardization）

为了让精灵（Sprite）能正确响应光照，必须升级美术资产管线。所有场景元素和角色将包含以下纹理贴图 ：

1. **Albedo Map（反照率贴图）：** 基础颜色，去除烘焙的光影。
2. **Normal Map（法线贴图）：** 记录表面的凹凸细节。对于2D游戏，通常需要预渲染或手绘法线。
3. **Mask Map（混合遮罩贴图）：** 利用RGBA通道复用数据：
   - **R - Roughness（粗糙度）：** 决定表面是哑光还是高光。
   - **G - Metallic（金属度）：** 区分金属与非金属材质。
   - **B - Height/AO（高度/环境光遮蔽）：** 用于视差遮挡（Parallax Occlusion）或自阴影计算。
   - **A - Emission（自发光）：** 用于魔法纹路或发光部件。

### 4.2 渲染路径选择：集群前向渲染（Clustered Forward+）

在ARPG中，半透明特效（半透明的幽灵、魔法火焰、UI光效）占据了画面的很大比例。传统的延迟渲染（Deferred Rendering）虽然在处理多光源上有优势，但无法高效处理半透明物体（G-Buffer只能存储一层深度），且带宽消耗巨大。

因此，V4架构将采用**集群前向渲染（Clustered Forward+）** 。

#### 4.2.1 视锥体分簇（Frustum Clustering）

1. **空间划分：** 将摄像机的视锥体切分为许多小的3D簇（Clusters/Voxels），例如在屏幕空间分为16x9个块，在深度方向分为24层。
2. **光照剔除（Light Culling）：** 每帧开始时，使用一个Compute Shader计算所有动态光源（火球、闪电、环境光点）与这些簇的相交情况。每个簇维护一个“光源列表”。
3. **着色（Shading）：** 在Fragment Shader中，像素根据自己的屏幕位置和深度值，计算出所属的簇ID，然后只读取该簇对应的光源列表进行光照计算。

#### 4.2.2 优势

- **透明度友好：** 前向渲染天然支持Alpha Blending，完美适配ARPG的特效需求。
- **海量光源：** 理论上支持场景中同时存在数千个动态光源，使得法师的每一个火花都能照亮周围的地面和战利品。

### 4.3 2.5D高度图光影（Height-Map Lighting）

为了解决2D游戏缺乏体积感的问题，我们将引入基于高度图的实时阴影技术 。

- **全局高度场：** 将场景中的地形高度、物体高度烘焙到一张全局高度图中（或动态合成）。
- **光线步进（Raymarching）：** 在Pixel Shader中，从当前像素向光源方向发射光线，并在高度图中采样。如果采样到的高度大于光线当前高度，则判定为阴影。
- **自投影：** 结合Sprite自身的Height Map，可以让角色的一只手投射阴影到自己的身体上，极大增强立体感。

## 5. V5长期规划：实时全局光照与辐射级联（Radiance Cascades）

V5阶段的野心是对标《流放之路2》展示的尖端技术——在2D平面上实现全动态的全局光照（Global Illumination, GI），让光线能够在墙壁、地板和物体之间反弹。

### 5.1 传统GI在2D中的挑战

传统的屏幕空间光线追踪（Screen Space Ray Tracing）或蒙特卡洛积分在计算漫反射（Diffuse Bounce）时，需要从每个像素发射大量光线来采样周围环境。要获得无噪点的图像，通常需要成百上千次采样，这在实时渲染中是不可接受的。

### 5.2 解决方案：辐射级联（Radiance Cascades）

辐射级联是近年来针对2D GI提出的一种革命性技术，其核心思想利用了光照的“半影假设”（Penumbra Hypothesis）：距离越远的光源，所需的空间分辨率越低，但角度分辨率要求越高（反之亦然）。

#### 5.2.1 级联架构（Cascade Architecture）

我们将GI计算分解为多个级联层（Cascades），通常为4-6层（Cascade 0 到 Cascade 5）。

- **Cascade 0（近场）：** 覆盖极短的距离（例如0-4像素）。它拥有最高的分辨率，但每个探针（Probe）只发射少量光线（例如4条）。
- **Cascade N（远场）：** 覆盖极远的距离（例如屏幕的一半）。它的空间分辨率很低（稀疏探针），但每个探针发射大量光线（或合并了低层级的光线信息）以捕捉来自各个方向的环境光。

#### 5.2.2 运行机制

1. **合并（Merge）：** 渲染过程从最高层级（最远距离）开始。计算结果通过双线性插值（Bilinear Interpolation）传递给下一层级。
2. **视差校正：** 在每一层，光线追踪不仅仅是寻找光源，更是将上一层级的辐射亮度（Radiance）“注入”到当前层级。
3. **结果：** 最终在Cascade 0输出时，我们得到了一张包含了无限反弹信息的高质量光照贴图，且每一帧的计算复杂度仅相当于几次纹理采样，完全避免了传统光追的噪点问题。

#### 5.2.3 配合JFA（Jump Flood Algorithm）

为了加速光线投射，我们需要一个快速查询“最近遮挡物距离”的数据结构。JFA算法可以在GPU上以$O(\log N)$的复杂度生成2D距离场（SDF）。辐射级联的光线在行进时，利用JFA生成的SDF进行空维跳跃（Space Skipping），从而极大地提升遍历效率 。

## 6. 实施路线图与技术栈建议

为了确保从V2平稳过渡到V5，建议按照以下阶段分步实施：

### 第一阶段：V3核心重构（预计耗时：3-5个月）

- **目标：** 解决CPU瓶颈，实现万级同屏单位不掉帧。
- **关键任务：**
  - [GPU] 实现`IndirectDrawManager`，封装MDI调用接口。
  - 开发离线MSDF字体生成工具，实现运行时`TextBatcherCS`计算着色器。
  - [Loot] 移植战利品逻辑到ECS架构，实现基于Compute Shader的物理避让布局。
  - [Engine] 引入Render Graph（渲染图）架构，管理复杂的Pass依赖和资源屏障。

### 第二阶段：V4画质升级（预计耗时：4-6个月）

- **目标：** 引入PBR工作流，提升光影质感。
- **关键任务：**
  - 重写Uber Shader，支持PBR材质模型（GGX分布）。
  - [Light] 实现Clustered Forward+的光源剔除算法。
  - 升级地图编辑器，支持放置点光源、聚光灯及烘焙高度图。

### 第三阶段：V5次世代技术预研（预计耗时：6个月+）

- **目标：** 动态GI与流体交互。
- **关键任务：**
  - [GI] 实现JFA距离场生成Pass。
  - [GI] 落地辐射级联（Radiance Cascades）管线。
  - 探索基于GPU的SPH流体模拟（用于血液、水面），并与GI系统交互。

------

## 7. 结论

通过将渲染架构从“CPU主导”转变为“GPU驱动”，我们不仅能够解决当前V2版本中存在的性能顽疾，更为未来的画质飞跃奠定了坚实基础。V3设计中对Compute Shader的深度应用，将彻底释放被战利品和文字渲染占用的CPU资源；而V4和V5规划则确保了引擎在未来3-5年内，能够在画面表现力上与世界顶级ARPG保持同步。这是一场从底层数据流到上层光照算法的全面革新，是实现高性能、高画质目标的必由之路。

## 8. 技术深度解析：从原理到实现

本章节将深入探讨前文提到的核心技术，补充具体的实现细节、数据结构定义及算法逻辑，旨在为工程团队提供可执行的参考手册。

### 8.1 深入解析：GPU驱动的文本渲染管线

在V3架构中，文本渲染的革新是性能优化的重中之重。

#### 8.1.1 字体图集生成与管理 (MSDF Implementation)

为了支持高质量的缩放，我们需要离线或运行时生成MSDF图集。

- **工具链：** 使用开源库如 `msdfgen` 。

- **数据结构：** 生成的纹理通常为RGB格式，每个通道存储不同方向的距离场。

  - `R`通道：左/右边缘的距离。
  - `G`通道：上/下边缘的距离。
  - `B`通道：对角线或其他辅助边缘。

- **Shader解码逻辑：**

  OpenGL Shading Language

  ```
  float median(float r, float g, float b) {
      return max(min(r, g), min(max(r, g), b));
  }
  
  float screenPxDistance = screenPxRange() * (median(sample.r, sample.g, sample.b) - 0.5);
  float opacity = clamp(screenPxDistance + 0.5, 0.0, 1.0);
  ```

  这段代码展示了如何在Fragment Shader中通过中值滤波从MSDF纹理中恢复锐利的边缘。

#### 8.1.2 并行前缀和排版 (Parallel Prefix Sum)

在Compute Shader中计算字符串中每个字符的X轴偏移量是一个典型的“前缀和”问题。

对于短字符串（如伤害数字，通常<10个字符），可以使用**Warp-level Intrinsics**（如Vulkan的`subgroupInclusiveAdd`或CUDA的`__shfl_up`）来实现极速计算，无需多Pass扫描。

- **算法逻辑：**

  1. 每个线程加载一个字符的`x_advance`。

  2. 调用子群（Subgroup）指令计算当前线程之前所有字符的`x_advance`之和。

  3. 结果即为当前字符的局部偏移坐标。

     这种方法避免了全局内存的原子操作，将排版耗时压缩到微秒级。

### 8.2 深入解析：多重绘制间接指令 (MDI) 与剔除

#### 8.2.1 间接命令结构 (Indirect Command Structure)

在Vulkan/OpenGL中，间接绘制缓冲区的内存布局必须严格匹配硬件要求。

C++

```
// C++ / Shader 共享结构定义
struct DrawElementsIndirectCommand {
    uint count;         // 要绘制的索引数量 (Index Count)
    uint instanceCount; // 实例数量 (Instance Count)
    uint firstIndex;    // 索引缓冲区的起始偏移
    int  baseVertex;    // 顶点缓冲区的基准偏移
    uint baseInstance;  // 实例ID的基准值
};
```

在V3中，我们不仅要生成这个结构，还要利用Compute Shader动态修改`instanceCount`。如果剔除逻辑判断某类物品全部不可见，直接将`instanceCount`置零，GPU渲染前端（Front-End）会自动跳过该Draw Call，实现零开销剔除 。

#### 8.2.2 剔除算法细节 (Culling Algorithms)

- **视锥剔除 (Frustum Culling)：** 将物体的包围球（Bounding Sphere）与六个视锥平面方程进行点积运算。

- **遮挡剔除 (Occlusion Culling) - HZB方案：**

  1. 上一帧的深度图生成多级Mipmap（Hi-Z Buffer）。

  2. 根据物体在屏幕上的投影大小，选择对应层级的深度图进行单次纹理采样比对。

  3. 如果物体的最浅深度 > Hi-Z深度，则物体被完全遮挡，剔除之。

     这种技术对于具有复杂地形（如多层地牢、墙壁遮挡）的ARPG尤为重要，能大幅减少Overdraw。

### 8.3 深入解析：2D PBR 光照模型

V4引入的PBR并非简单的3D PBR照搬，而是针对2D Sprite优化的简化模型。

#### 8.3.1 法线分布函数 (NDF)

对于2D Sprite，我们通常假设表面法线主要朝向Z轴（屏幕外），但在边缘处根据Normal Map发生偏转。标准GGX分布可能对于“纸片人”过于强烈。

- **优化方案：** 采用**Trowbridge-Reitz (GGX)** 分布，但在粗糙度（Roughness）映射上进行调整，避免在Sprite边缘产生不自然的菲涅尔高光（Fresnel Rim）。

#### 8.3.2 2D环境光遮蔽 (Sprite-Based AO)

除了屏幕空间AO（SSAO），我们还需要基于Sprite自身几何的AO。

- **离线烘焙：** 在美术制作阶段，根据Sprite的深度信息烘焙AO通道。
- **运行时合成：** 结合SSAO，使得当角色靠近墙壁时，不仅墙壁变暗，角色靠近墙壁的一侧也会受到遮蔽，增强融合感 。

### 8.4 深入解析：辐射级联 (Radiance Cascades) 技术细节

V5的辐射级联技术是基于最新的图形学研究 。

#### 8.4.1 探针与层级设计 (Probes & Hierarchy)

- **层级 0 (Level 0)：** 分辨率与屏幕1:1。探针间隔为1像素。每个探针发射4条射线，覆盖 $[0, \frac{\pi}{2})$ 的角度区间（假设四路对称）。射线长度极短（例如4像素）。
- **层级 1 (Level 1)：** 分辨率是屏幕的1/4（宽高各半）。探针间隔为2像素。射线长度增加一倍（8像素），覆盖角度相同，但代表的空间范围更大。
- **层级 N (Level N)：** 分辨率极低，负责收集整个屏幕范围的全局光。

#### 8.4.2 双线性合并与平滑 (Bilinear Merging)

核心难点在于如何将低分辨率层级的光照无缝融合到高分辨率层级。

- **算法：** 在计算层级 $i$ 时，着色器会采样层级 $i+1$ 的纹理。由于层级 $i+1$ 的探针位置与层级 $i$ 不对齐，必须使用双线性插值，不仅在空间上插值（Spatial），还要在角度上插值（Angular）。
- **去噪：** 由于每一层只负责一部分光程，且高频细节（近处阴影）由高分辨率层级（L0）处理，低频信息（环境光）由低分辨率层级（LN）处理，最终合成的结果天然具有极低的噪点，无需传统光追的复杂时域降噪（TAA/Denoiser）。

### 8.5 内存管理与架构权衡

在实施上述技术时，必须仔细考量显存带宽与占用。

| **资源类型**            | **估算大小 (1080p)** | **带宽压力** | **优化策略**              |
| ----------------------- | -------------------- | ------------ | ------------------------- |
| **G-Buffer (Deferred)** | ~32MB/帧             | 极高 (读写)  | 放弃，改用 Forward+       |
| **Cluster Buffer**      | ~1MB                 | 低           | 使用 3D Texture 或 SSBO   |
| **Radiance Cascades**   | ~50MB (所有层级)     | 中           | 使用 FP16 格式，复用纹理  |
| **MSDF Font Atlas**     | 4MB (4096^2, 单通道) | 极低         | BC4/BC5 压缩              |
| **Loot Buffer**         | ~10MB (10万物品)     | 低           | 仅上传脏数据 (Dirty Data) |

**架构决策：** 鉴于2D ARPG通常对半透明特效的高需求（技能特效满天飞），以及现代GPU计算能力的提升，**Clustered Forward+** 结合 **Bindless Textures** 是最佳的架构选择。它避免了Deferred架构中G-Buffer读写带来的巨大带宽开销（这在移动端或中低端PC上尤为致命），同时保留了多光源支持的能力。

## 9. 总结

本报告详细阐述了从V2到V5的完整技术演进路线。通过V3的GPU驱动架构重构，我们首先解决了“生存问题”——即在海量单位下的性能瓶颈；通过V4的PBR化，我们解决了“面子问题”——提升画面的材质感与立体感；最后通过V5的辐射级联GI，我们解决了“未来问题”——实现动态、统一、且性能可控的全局光照。

这一系列变革不仅仅是代码层面的重写，更是对渲染管线认知的升级。实施这一规划，将使我们的引擎具备与国际顶级ARPG同台竞技的核心技术实力。
