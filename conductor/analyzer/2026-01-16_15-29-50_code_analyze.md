# Code Risk Analysis Report
Date: 2026-01-16 14:00:00

## Summary
The codebase is generally well-structured with modern C++20 practices. However, critical safety risks were identified in the SkillSystem related to EnTT iterator invalidation, and resource leaks were found in the new GPUFlowFieldSystem.

## Critical Risks (High Priority)
### 1. Use-After-Free (UAF) in SkillSystem::UpdateStates
- **Location**: src/game/systems/skill/SkillSystem.cpp:862
- **Description**: The loop or (auto entity : view) holds a reference uto &exec = view.get<SkillExecution>(entity); while calling hook(registry, entity, exec). If a hook (e.g., PhantomFlash counter or BehaviorInjection) triggers the creation of a NEW entity with SkillExecution component, the SkillExecution pool may reallocate.
- **Consequence**: The exec reference becomes a dangling pointer. Subsequent access like exec.state = ... (L871) will cause a Heap Corruption or Crash.
- **Recommendation**: 
    1. Do NOT pass exec by reference to hooks if hooks can modify the registry structure.
    2. Or, iterate and collect entities first, then process them (though this doesn't save the reference).
    3. Safest: Re-fetch the component inside the loop after hooks, OR ensure hooks cannot create SkillExecution components (hard to enforce).
    4. **Fix**:
    `cpp
    auto view = registry.view<SkillExecution>();
    // Collect entities to avoid iterator invalidation of the view itself
    std::vector<entt::entity> entities(view.begin(), view.end()); 
    for(auto entity : entities) {
        if(!registry.valid(entity)) continue;
        auto& exec = registry.get<SkillExecution>(entity); // Refetch safe? No, if realloc happens during hook.
        // ...
    }
    `
    Actually, just re-fetching egistry.get<SkillExecution>(entity) *after* the hook call is safer if we passed it by pointer/ref to the hook. But if the hook invalidated it, the reference passed to the hook *during* the hook execution might invalidate? No, only if the hook *causes* the realloc.
    **Better Fix**: Run hooks that might spawn entities *outside* the update loop of the component they spawn.

### 2. Memory Leak in GPUFlowFieldSystem::Shutdown
- **Location**: src/engine/render/GPUFlowFieldSystem.cpp:231
- **Description**: m_integrationBuffer2 and m_densityBuffer are created in Init but are NOT released in Shutdown.
- **Consequence**: VRAM leak (SSBOs) upon game exit or system reload.
- **Recommendation**: Add m_integrationBuffer2.Release(); and m_densityBuffer.Release(); to Shutdown.

## Performance Bottlenecks
### 1. Vector Reallocation in GPUFlowFieldSystem::Update
- **Location**: src/engine/render/GPUFlowFieldSystem.cpp:108
- **Description**: std::vector<uint32_t> costInt is constructed (allocated) every frame.
- **Consequence**: Unnecessary heap allocation overhead every frame.
- **Recommendation**: Make costInt a member variable m_costIntCache and esize/clear it to reuse capacity.

## Refactoring Suggestions
- **EnTT Safety**: Adopt a strict pattern of 'Collect entities -> Iterate Collection' for all Systems that modify the registry structure (create/destroy) during updates.
- **Resource Management**: Verify core::ComputeBuffer has a destructor that calls Release() to automate safety (RAII). If not, implement it.
