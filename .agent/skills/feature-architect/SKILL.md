# Feature Architect (NoMoreDay Edition)

## 1. 开发协议 (The Dev Protocol)
所有重大功能变更必须严格遵循以下两个阶段。严禁在未经授权的情况下直接开始 Phase 2。

### Phase 1: 设计方案 (Spec/Plan)
在修改任何 C++ 源文件前，必须在对应的 track 目录下生成并提交 `spec.md` 和 `plan.md`。

**强制性内容要求：**
- **技术规格书 (Spec)**:
    - **严禁笼统**: 不得使用“更新系统逻辑”等模糊词汇。
    - **公式化**: 战斗/数值变更必须提供完整的数学公式和示例数据表。
    - **性能量化 (优化任务必备)**: 必须列出“问题陈述表”和“目标指标表”（当前基线 vs 优化目标）。
    - **代码先行**: 必须包含 `struct`、`enum` 或 `namespace` 的具体 C++ 定义。
    - **验收清单**: 必须提供可量化的检查项。
- **实现计划 (Plan)**:
    - **原子化任务**: 将开发拆分为 Phase，每个任务必须有明确的 ID 和 **预估工时 (h)**。
    - **阶段绰号**: 为每个 Phase 起一个能代表技术手段的绰号（如 `The Batching`, `The DOD`）。
    - **验证目标**: 在 Phase 中必须包含具体的性能验证目标值（如 `ScopedTimer < 1ms`）。
    - **依赖关系**: 必须指明任务间的先后顺序。
    - **风险评估**: 预判可能的性能、架构或兼容性风险。

*参考模板请查看：`references/templates.md`*

### Phase 2: 实现与测试 (Implementation)
只有在 Phase 1 获准后才能开始。
- **测试先行**: 优先编写 `tests/` 下的骨架代码。
- **增量实现**: 保持原子级提交，每次修改后必须验证编译。
- **审计合规**: 确保所有修改符合 `code_standard.md`。

## 2. ECS 与 DOD 准则
- **POD 组件**: 组件仅包含数据，严禁复杂成员。
- **系统隔离**: 逻辑仅在 System 中，数据仅在 Component 中。
- **主循环零分配**: Update/Render 路径严禁任何形式的堆内存分配。

## 3. 语言与沟通
- **中文回复**: 所有规格书、计划书和沟通必须使用中文。
- **专业术语**: 在代码注释或技术文档中，保留必要的英文术语（如 `Simd`, `SSBO`, `Culling`）。

## 4. 交付清单 (Definition of Done)
1. `spec.md` 和 `plan.md` 完整且经过用户确认。
2. 代码实现通过编译，无新产生的 Warning。
3. 单元测试与集成测试全部通过。
4. 经过 `code-risk-analyzer` 的风险评估。
