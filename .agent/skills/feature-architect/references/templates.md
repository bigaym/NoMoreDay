# Feature Architect 交付模板

## 1. 技术规格书 (Spec.md) 模板

```markdown
# [功能名称] - 技术规格书

## 1. 概述
简述功能目标。
### 1.1 设计目标
| 目标 | 描述 |
|-----|-----|
| 目标 A | ... |

## 2. 核心逻辑与公式 (如有)
如果是战斗或数值系统，必须列出精确的数学公式：
- **公式名称**: `result = (base + flat) * (1 + inc) * more`
- **示例数据**: 列出在 Area Level 100 时的预期表现。

## 3. 数据结构变更 (DOD)
直接给出 C++ 代码块，定义新的 Component 或 Constant：
```cpp
namespace NoMoreDay::Constants::Example {
    constexpr float VALUE = 1.0f;
}

struct ExampleComponent {
    float data;
};
```

## 4. 系统修改清单
明确哪些文件、哪些函数需要改动：
| 文件 | 函数/位置 | 修改内容描述 |
|-----|----------|------------|
| `StatsSystem.cpp` | `BakeStats()` | 集成新的计算公式 |

## 5. API 契约
暴露给其他系统的公共接口定义。

## 6. 测试矩阵
| 测试类型 | 覆盖内容 | 预期结果 |
|---------|---------|---------|
| Unit | 公式边界值 | 通过断言 |

## 7. 验收标准
- [ ] 关键数值符合预期
- [ ] UI 正确显示新字段
- [ ] 性能测试无明显下降
```

## 3. 性能优化专项 (Optimization Spec/Plan)

### 3.1 优化规格书 (Spec) 特有项
在基础 Spec 之上，必须包含：
- **问题陈述表**: 明确 P1/P2 级别，关联具体的风险等级 (🔴/🟡)。
- **目标指标表**: 对比“当前基线”与“优化目标”，并说明测量方法。
- **技术原理**: 使用“核心思想”+“技术实现”两步法描述。

### 3.2 优化计划书 (Plan) 特有项
在基础 Plan 之上，必须包含：
- **阶段化命名**: Phase 必须起一个概括性的绰号，如 `Phase 1: 粒子异步化 (The Unblocking)`。
- **Scoped 验证**: 必须包含具体的日志测量目标，例如 `目标: < 500μs`。
- **基准测试 (The Audit)**: 最后一个 Phase 必须是全量对比测试。
