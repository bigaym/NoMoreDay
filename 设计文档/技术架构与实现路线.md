## 2. 系统总览

### 2.1 分层原则

1. Gameplay 与 Render 解耦。
2. 战斗数值与动作落地解耦（`DamagePipeline` vs `CombatSystem`）。
3. 配置合同与运行逻辑解耦（合同校验脚本 + CI 门禁）。

### 2.2 帧序（硬约束）

必须保持：

`Input -> Player Movement -> AI -> Combat -> Spatial Grid Rebuild -> Physics -> Render`

Render 阶段入口为 `RenderSystem::Render()`，内部统一走 RenderGraph。

## 3. 战斗架构（vNext，已落地）

1. `DamagePipeline`：唯一数值入口，接入 `added_damage_effectiveness` 与 `trigger.effectiveness`。
2. `CombatSystem`：生命/屏障结算与死亡流转。
3. `AilmentEngine`：异常状态合同化。
4. `ProcBudgetManager`：触发/击回/异常/事件预算治理。
5. `SummonSystem`：召唤生命周期、AI、战斗桥接与归因。
6. `CombatTelemetry`：正确性与性能指标采样。

## 4. GPU 渲染架构（v5 基线）

### 4.1 版本与契约

1. GPU ABI：`GPU_ABI_VERSION = 5`（`src/engine/render/GPUData.hpp`）。
2. RenderGraph 契约：`RENDERGRAPH_CONTRACT_VERSION = 3`（`src/engine/render/graph/RenderGraph.hpp`）。
3. 图形 API：OpenGL 4.3+，Windows + MSVC-only。

### 4.2 渲染模块结构（代码真实路径）

```text
src/engine/render/
├── RenderSystem.*                 # 渲染主入口与 Pass 编排
├── graph/RenderGraph.*            # Build/Execute/Validate
├── passes/*.hpp/*.cpp             # Scene/Lighting/GI/PostProcess/Composite...
├── core/RenderConstants.hpp       # RenderConfig / QualityTier / 预算常量
├── RenderConstants.hpp            # SSBO/Barrier/Texture/容量常量
├── GPUData.hpp                    # GPU ABI 结构体与版本
├── GPUEntitySystem.*              # 实体 GPU 同步
├── MDIRenderer.*                  # MDI 绘制
├── GPUTextSystem.* / GPULootSystem.* # V4 GPU 文本/战利品
├── lighting/ shadow/ gi/          # 光照/阴影/GI 子模块
└── resources/                     # FBO/Transient/全屏资源管理
```

### 4.3 RenderGraph 资源与所有权合同

RenderGraph 使用资源标签和 owner 标签进行校验：

1. 资源标签：`SceneHdrColor`、`SceneDepth`、`PostProcessLdrColor`、`DistortionLdrColor`、`FinalOutputColor`、`OccluderMask`、`DistanceField`、`EmissiveBuffer`、`RadianceMap`。
2. 所有权标签：`Scene`、`Lighting`、`HeightShadow`、`OccluderExtract`、`JFA`、`RadianceCascades`、`GIComposite`、`FluidSimulation`、`Volumetric`、`VFX`、`UIWorld`、`PostProcess`、`Distortion`、`Composite`。
3. 约束：首次写入者、可写 owner、多写入合法性、读前写检测都在 `RenderGraph::ValidateBuildContracts()` 中强校验；Debug 下校验失败会抛异常。
4. 输出约束：仅 `Composite` owner 可写 `FinalOutputColor`（BackBuffer）。

### 4.4 当前渲染 Pass 顺序（以 `RenderSystem.cpp` 为准）

基础顺序：

`Scene -> (ShadowPrepare/Build/Resolve + LightCulling) -> Lighting -> HeightShadow -> (OccluderExtract -> JFA -> RadianceCascades -> GIComposite) -> FluidSimulation(可选) -> Volumetric(可选) -> VFX -> GPUText(可选) -> GPULoot(可选) -> UIWorld -> PostProcess -> Distortion(可选) -> Composite`

说明：

1. GI、流体、体积光、GPUText、GPULoot、Distortion 都是按 `RenderConfig` 条件启停。
2. `CompositePass` 根据可用输入自动选择 `Distortion` / `PostProcess` / `SceneHDR` 结果。

### 4.5 SSBO / Image 绑定治理

1. 全局 SSBO 绑定枚举覆盖 0-15（`RenderConstants::Binding`），其中 `SSBO_LOOT_INSTANCE = 15`；16 个 binding 预算已占满。
2. `BindingGovernance::kGlobalSharedSSBOBindings` 对共享槽位做去重静态检查。
3. 新增数据优先使用 Compute 本地 binding 或时间片复用，不新增全局常驻绑定。
4. V5 GI 使用独立 image binding 0-5（Occluder/Seed/Distance/Emissive/Radiance）。

### 4.6 Quality Tier 与 Feature Flag

1. Tier：`Low / Medium / High / Ultra`（`core/RenderConstants.hpp`）。
2. 关键开关：`v3Enabled`、`clusteredLightingEnabled`、`clusteredLightingV4Enabled`、`heightShadowEnabled`、`gpuTextEnabled`、`gpuLootEnabled`、`giEnabled`、`fluidEnabled`、`distortionEnabled`、`volumetricLightEnabled` 等。
3. 自动降级序列在 `QualityTierManager` 中实现：`ReduceBloom -> DisableDistortion -> LimitDynamicLights -> ReduceClusteredPressure -> HybridShadowToSDF -> DisableHighMaterialBranch`。

### 4.7 ABI 生成与治理链路

1. C++ 结构体：`src/engine/render/GPUData.hpp`
2. 清单：`tools/render_abi/abi_manifest.json`
3. 生成：`tools/render_abi/generate_gpu_abi.py`
4. 输出：`assets/shaders/generated/gpu_abi.glslinc`
5. 校验：`GPUABIContract` + analyze 阶段脚本检查（禁止手写 ABI struct 漂移）

## 8. 统一修饰器运行时系统（UMR）

新增权威参考：

- `设计文档/统一修饰器运行时系统_UMR.md`
- `src/game/systems/modifier/*`
- `assets/data/modifier_v2/*`

UMR（Unified Modifier Runtime）是玩家侧修饰执行的统一底座，已将装备词缀、技能专精、天赋节点迁移到同一执行链路。

架构原则：

1. 内容配置（JSON）与运行时执行（binary runtime）解耦。
2. 适配器只负责收集上下文和 record id，业务效果由 `ModifierEvaluator` 统一解释。
3. 新修饰逻辑禁止新增旁路，必须落到 UMR 的 filter/op 模型。

当前状态（2026-03-01）：

1. 玩家侧 UMR 一期：DONE。
2. 地图词缀/怪物词缀（属性修饰）并轨：DONE。
3. 怪物行为词缀并轨：IN PROGRESS（Update/Hit/Death 事件门禁已走 `MonsterModifierAdapter -> ModifierEvaluator`；`Storm`/`Void`/`Molten`/`Teleporter`/`Frozen`/`Berserker`/`VoidZone`/`ManaSiphon`/`Shielding`/`Vortex`/`Waller`/`Suppressor`/`SoulLink`/`Vampiric`/`Nullifier`/`Entangler`/`MirrorImage`/`StormStrider`/`Toxic`/`SoulEater`/`Avenger` 已接入 Op 优先分发，其余处理器仍在 `MonsterAffixSystem`）。
