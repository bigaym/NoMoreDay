# 2D 暗黑Like Roguelite ARPG - 存档与持久化系统设计 V1.0

## 1. 核心设计理念

为满足 **10,000+ 实体** 的高性能需求，并结合 **Roguelite** 的游戏机制，本系统采用 **"城镇仅限 (Town-Only)"** + **"异步快照 (Async Snapshot)"** 的策略。

### 1.1 存盘策略 (Save Strategy)
*   **回城自动保存 (Auto-Save on Return)**：当玩家穿越传送门回到城镇时，强制触发自动保存。
*   **城镇手动保存 (Manual Save in Town)**：仅在城镇中允许通过菜单手动保存并退出。
*   **地牢无状态 (Stateless Dungeon)**：地牢内的战斗状态（怪物位置、飞行道具、掉落物）**不予持久化**。
    *   **理由**：序列化数万个动态实体的开销极大且容易出错（Handle失效问题）。 roguelite 的机制允许我们丢弃单次 Run 的中间状态，只需保留“玩家收益”和“当前层数/种子”。
    *   **异常处理**：若在地牢中途崩溃或强退，视为“撤退”或“死亡”（根据设计决定），回滚至上次出城/进城的状态。

### 1.2 高性能 I/O (High-Performance I/O)
*   **异步写入**：使用 `Taskflow` 将文件 I/O 放入后台线程，避免阻塞渲染线程（即避免“卡顿”）。
*   **原子化操作**：先写入 `.tmp` 临时文件，写入完成后重命名为 `.json`，防止掉电导致存档损坏。
*   **数据快照**：在主线程逻辑帧结束时，瞬间构建一个 `SaveDataDTO` 纯数据对象（Deep Copy），然后将该对象交给后台线程序列化。

## 2. 存档文件结构 (File Structure)

存档分为 **全局数据 (Account Scope)** 和 **角色数据 (Character Scope)**。

### 2.1 目录结构
```text
saves/
├── global.json          # 全局设置、成就、传家宝宝库 (HeirloomVault)
├── slot_0.json          # 角色存档 0
├── slot_1.json          # 角色存档 1
├── ...
└── temp/                # 临时文件目录 (用于原子写入)
```

### 2.2 全局存档 (`global.json`)
*   **Settings**: 音量、分辨率、按键绑定、高分榜记录。
*   **Unlocks**: 已解锁的职业、难度等级、成就。
*   **HeirloomVault**: 传家宝宝库数据 (复用 `HeirloomVault::save` 逻辑)。

### 2.3 角色存档 (`slot_X.json`) - 聚合结构
这是一个巨大的 JSON 对象，包含玩家的所有状态。

```json
{
  "version": 1,
  "timestamp": 1736916522,
  "playtime": 3600.5,
  "header": {
    "name": "BladeMaster_01",
    "class": "SwordCultivator",
    "level": 10,
    "difficulty": 1
  },
  "stats": { ...PlayerStats... },
  "transform": { "x": 100, "y": 200, "mapId": "Town_01" },
  "inventory": [ ...SerializedItemDTOs... ], 
  "equipment": { "MainHand": ...SerializedItemDTO..., "Chest": ... },
  "skills": { ...ActiveSkillsComponent... },
  "astrolabe": { ...AstrolabeComponent... },
  "quests": { ...QuestState... }
}
```

## 3. 数据序列化方案 (Data Schemas)

由于 ECS 的 `entt::entity` 是运行时 ID，不可持久化，所有引用必须在保存时转换为 **Data Object (DTO)**，加载时重建。

### 3.1 物品序列化 (Item Serialization) - 快照模式
为了确保存档的长期兼容性与确定性，我们**放弃**仅仅保存 Seed 的方案，改为**全量属性快照 (Full Attribute Snapshot)**。
这意味着我们将序列化物品生成的最终属性值（如攻击力、防御力、具体词缀数值），而非仅仅保存生成参数。

#### SerializedItem DTO
```cpp
struct SerializedItem {
    // 基础信息
    uint32_t itemId;           // Config ID
    int quantity;
    uint64_t instanceId;       // 唯一实例ID (用于追踪)

    // 属性快照 (Snapshot) - 直接保存生成后的最终值
    struct StatsSnapshot {
        int level;
        Rarity rarity;
        float attack;          // 最终基础攻击力
        float defense;         // 最终基础防御力
        EquipmentSlot slot;
        int forgingPotential;
        float value;           // 金币价值
    } stats;

    // 词缀数据 (显式保存 Type + Tier + Value)
    struct SavedAffix {
        AffixType type;
        int tier;
        float value;        // 确定的数值
        bool isPrefix;
        bool isLegendary;
    };
    std::vector<SavedAffix> affixes;
    std::vector<SavedAffix> implicits;
    
    // 镶嵌物 (递归)
    std::vector<SerializedItem> socketedItems;
};
```

**优势**:
*   **版本鲁棒性**: 即使未来版本修改了词缀权重或 ItemFactory 算法，旧存档的装备属性保持不变。
*   **所见即所得**: 避免了“加载后数值微调”的潜在 Bug。

### 3.2 技能与星盘 (Skills & Astrolabe)
现有组件 (`ActiveSkillsComponent`, `AstrolabeComponent`) 已经支持简单的 `nlohmann::json` 序列化。
*   **需要注意**：`ActiveSkillsComponent` 中的 `SpecializedSkill` (技能专精树) 包含 `unordered_map<uint32, int>`，可以直接序列化。
*   **快捷键栏**：`SkillSlot` 数组直接保存。

### 3.3 玩家属性 (Player Attributes)
直接序列化 `PlayerStats` 组件 (包含 Level, XP, Base Attributes)。
*   **衍生属性** (如 `TotalAttack`) **不需要保存**。加载游戏后，`StatsSystem` 会根据 Base Attributes + Equipment + Skills 重新计算所有衍生属性。

## 4. 系统架构设计 (Architecture)

### 4.1 SaveManager (单例/系统)

```cpp
class SaveManager {
public:
    // API
    std::future<bool> saveCharacterAsync(entt::registry& registry, int slotIndex);
    bool loadCharacter(entt::registry& registry, int slotIndex);
    
private:
    // Helper to capture state from ECS to DTO
    CharacterSaveData createSnapshot(entt::registry& registry);
    
    // Helper to restore ECS from DTO
    void restoreFromSnapshot(entt::registry& registry, const CharacterSaveData& data);
};
```

### 4.2 存档流程 (Save Flow)
1.  **触发**：用户点击“保存”或触发回城。
2.  **快照 (Main Thread)**：
    *   获取 `PlayerEntity`。
    *   Deep Copy `PlayerStats`, `Transform`, `AstrolabeComponent`。
    *   遍历 `InventoryComponent`，查找所有 Item Entities，并在内存中构建 `vector<SerializedItem>`。
    *   **耗时**：极短 (< 1ms)，因为只是内存拷贝。
3.  **写入 (Taskflow Thread)**：
    *   将 `CharacterSaveData` 序列化为 JSON 字符串。
    *   写入 `saves/temp/slot_0.tmp`。
    *   `std::filesystem::rename` 覆盖原文件。
    *   **耗时**：10-100ms (取决于磁盘)，完全不阻塞主线程。

### 4.3 加载流程 (Load Flow)
1.  **读取**：读取 JSON 文件到内存 (Taskflow 可预读，但通常在Loading Screen同步读取)。
2.  **重建世界 (Main Thread)**：
    *   `registry.clear()` 清空世界。
    *   创建 `PlayerEntity`。
    *   应用 `PlayerStats`, `Astrolabe` 等组件。
    *   **重建物品**:
        *   遍历 `inventory` 数组中的 `SerializedItem` DTO。
        *   调用 `ItemFactory::restoreItem(serializedItem)`。
            *   该函数使用 `registry.create()` 创建新实体。
            *   **直接填充** `ItemComponent` 的数值字段 (Attack, Defense, Affixes)，**禁止** 触发随机生成逻辑。
        *   将新 Entity 加入 `InventoryComponent`。
        *   将新生成的 `entity` 放入 `InventoryComponent`。
    *   **强制刷新**：调用 `StatsSystem::update(0.0f)` 强制重算一次所有属性。

## 6. 关于性能的备注
对于本游戏规模：
*   **Reflctionless Serialization**: 我们使用手写的 `to_json/from_json` (nlohmann 宏)，这比运行时反射快得多。
*   **JSON vs Binary**: 鉴于存档只在回城时发生，且数据量 < 1MB，JSON 的解析速度 (通常 3-5ms) 完全可以接受，且便于开发调试。如有必要，可一键切换为 `nlohmann::json::to_cbor` (Binary Format)。
