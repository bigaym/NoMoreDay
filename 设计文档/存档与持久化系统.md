# 2D 暗黑Like Roguelite ARPG - 存档与持久化系统设计 V1.0

## 1. 核心设计理念

为满足 **10,000+ 实体** 的高性能需求，并结合 **Roguelite** 的游戏机制，本系统采用 **"城镇仅限 (Town-Only)"** + **"异步快照 (Async Snapshot)"** 的策略。

### 1.1 存盘策略 (Save Strategy)
*   **回城自动保存 (Auto-Save on Return)**：当玩家穿越传送门回到城镇、且存在进行中的裂缝时，由 `PortalSystem` 记录退出点并通过 `SharedContext::requestSave` 触发自动保存。
*   **城镇手动保存 (Manual Save in Town)**：仅在城镇中允许通过菜单手动保存并退出。
*   **地牢无状态 (Stateless Dungeon)**：地牢内的战斗状态（怪物位置、飞行道具、掉落物）**不予持久化**，仅保留维度实例数据（`ActiveDimensionalState`：种子、生物群系、层数、词缀与碎片快照等）。
    *   **理由**：序列化数万个动态实体的开销极大且容易出错（Handle失效问题）。 roguelite 的机制允许我们丢弃单次 Run 的中间状态，只需保留“玩家收益”和“当前层数/种子”。
    *   **裂缝退出点**：在裂缝进行中返回城镇时记录玩家离开时的位置 `lastExitPosition`，再次进入该裂缝时将玩家放置于该点。
    *   **异常处理**：若在地牢中途崩溃或强退，视为“撤退”或“死亡”（根据设计决定），回滚至上次出城/进城的状态。

### 1.2 高性能 I/O (High-Performance I/O)
*   **异步写入**：使用 `Taskflow` 将文件 I/O 放入后台线程，避免阻塞渲染线程（即避免“卡顿”）。
*   **原子化操作**：先写入 `saves/temp/*.tmp` 临时文件，校验文件大小后原子重命名为目标 `.nmd` 文件；覆盖已有文件前先将其备份为 `.bak`（备份失败则中止该次保存以保护原档），防止掉电或写入中断导致存档损坏。
*   **回退读取**：主文件缺失或校验失败时，自动尝试同名的 `.bak` 备份文件。
*   **数据快照**：在主线程逻辑帧结束时构建 `CharacterSaveData` 纯数据对象，并对 `ItemStorageService` 做深拷贝，然后将副本交给后台线程序列化。
*   **完整性校验与加密**：文件不加密、不压缩；通过 CRC32 校验文件头与各数据段，损坏的存档会被拒绝加载。

## 2. 存档文件结构 (File Structure)

存档分为 **全局数据 (Account Scope)** 和 **角色数据 (Character Scope)**。

### 2.1 目录结构
```text
saves/
├── global.nmd           # 全局存档（共享仓库）
├── slot_0.nmd           # 角色存档 0
├── slot_0.nmd.bak       # 角色存档 0 的备份
├── slot_1.nmd           # 角色存档 1
├── ...
├── quicksave.nmd        # 快捷存档（槽位 -1）
└── temp/                # 临时文件目录 (用于原子写入)
```

### 2.2 全局存档 (`global.nmd`)
全局存档仅承载 **共享仓库 (SharedStash)** 及其关联的物品实例、模板指纹、侧表与技能修正数据，独立于任何角色档。

其余按“账号”归属的数据由各自的子系统单独持久化：
*   **Settings**: 音量、分辨率、按键绑定等写入 `settings.json`。
*   **成就 (Achievements)**: 写入 `saves/achievements.json`。
*   **排行榜 (Leaderboard)**: 写入 `saves/leaderboard.json`。
*   **传家宝宝库 (HeirloomVault)**: 由 `ItemStorageService` 的传家宝容器承载，随角色档持久化（全局存档的脏段掩码不包含该段）。

### 2.3 角色存档 (`slot_X.nmd`) - 聚合结构
角色档为二进制单轨文件，其中“进度段 (ProgressionData)”内嵌一段 JSON，由 `CharacterSaveData` 序列化而来，schema 版本为 4。

```json
{
  "header": {
    "name": "玩家0",
    "characterClass": "SwordCultivator",
    "level": 10,
    "playtime": 3600,
    "timestamp": 1736916522,
    "version": 4
  },
  "primaryStats": { ...PrimaryStats... },
  "position": { ...Position... },
  "mapId": "Town_01",
  "skills": { ...ActiveSkillsComponent... },
  "skill_contract_runtime": {
    "version": 1,
    "skills": [
      {
        "skill_id": 101,
        "active_transmuter_node": 0,
        "trigger_cooldowns": [ { "node_id": 3, "remaining": 1.25 } ]
      }
    ]
  },
  "astrolabe": { ...AstrolabeComponent... },
  "combatHistory": { ...PlayerCombatHistory... },
  "blade_mastery": { ...BladeMasteryComponent... },
  "blade_resource": { ...BladeResourceComponent... },
  "blade_signature_skill": { ...BladeSignatureSkillComponent... }
}
```

物品容器（背包、装备、个人仓库、共享仓库、传家宝宝库、材料银行）不在此 JSON 中，而由同文件的二进制物品段承载。`blade_mastery`、`blade_resource`、`blade_signature_skill` 为可选字段，仅在对应组件存在时写入。

## 3. 数据序列化方案 (Data Schemas)

由于 ECS 的 `entt::entity` 是运行时 ID，不可持久化，物品引用统一通过 `ItemStorageService` 的 `ItemHandle`（索引 + 代次）在存档中表达，加载后再重建。

### 3.1 物品序列化 (Item Serialization) - 二进制单轨
物品统一由 `ItemStorageService` 持有，存档不存在独立的物品 DTO：物品以 POD 结构 `ItemInstance`（192 字节、trivially copyable）存储在物品库中，各容器（背包、装备、个人仓库、共享仓库、传家宝宝库、材料银行）只保存 `ItemHandle`，因此 `entt::entity` 不会被写入存档。

*   **属性快照**：`ItemInstance` 保存物品生成后的最终属性与词缀，加载时直接还原，不触发任何随机生成。
*   **文件格式**：`ItemPersistenceCodec` 将 `ItemStorageService` 编码为二进制 `.nmd` 文件，按数据段 (Section) 组织：
    `TemplateFingerprint`、`ItemInstances`、`ItemSideTables`、`Inventory`、`Equipment`、`BagSlots`、`PersonalStash`、`SharedStash`、`HeirloomVault`、`MaterialBank`、`EconomyMetadata`、`ProgressionData`、`ItemSkillModifiers`。
*   **增量保存**：编码时可传入脏段掩码与段缓存，仅重写发生变化的段。
*   **进度数据**：玩家角色数据 (`CharacterSaveData`) 以 JSON 载荷写入 `ProgressionData` 段，详见 2.3。

### 3.2 技能与星盘 (Skills & Astrolabe)
`ActiveSkillsComponent` 与 `AstrolabeComponent` 通过 `nlohmann::json` 序列化，随 `CharacterSaveData` 写入 `ProgressionData` 段。
*   **专精树**：`ActiveSkillsComponent` 中的 `SpecializedSkill` 包含 `unordered_map<uint32, int>`，直接序列化。
*   **快捷键栏**：`SkillSlot` 数组直接保存。
*   **技能契约运行时**：`SkillContractRuntimeComponent` 以 `SkillContractRuntimeSaveData` 形式保存各技能的活动转换节点与触发冷却剩余时间。

### 3.3 玩家属性 (Player Attributes)
角色档保存 `SaveHeader`（等级、游戏时长等）与 `PrimaryStats`（基础属性）。
*   **衍生属性** (如 `TotalAttack`) **不需要保存**。加载后由 `StatsDirty` 标记触发 `StatsSystem`，依据基础属性 + 装备 + 技能重新计算。

### 3.4 版本策略 (Versioning)
*   **角色档版本**：由 `CURRENT_CHARACTER_SAVE_VERSION`（当前为 4）定义，写入 `SaveHeader::version`。加载时若存档版本与当前版本不相等，直接拒绝加载并记录错误，不做迁移。
*   **物品存储版本**：由 `ITEM_STORE_BINARY_VERSION`（当前为 1）定义，写入二进制文件头。解码时若版本不匹配则拒绝加载。
*   **文件魔数**：二进制文件头以 `ITEM_STORE_MAGIC`（`'NMDS'`）标识。

### 3.5 完整性校验与加密 (Integrity)
*   **不加密、不压缩**：存档以明文二进制写入。
*   **CRC32 校验**：采用 IEEE 802.3 多项式（`0xEDB88320`），对段头表与每个数据段分别计算 CRC32；任一段校验失败即拒绝加载，且在全部校验通过前不修改内存中的物品数据。
*   **结构校验**：文件头魔数、段数量、段偏移与长度的合法性均在解码阶段校验。

## 4. 系统架构设计 (Architecture)

### 4.1 SaveManager (单例/系统)

```cpp
class SaveManager {
public:
    // API
    std::future<bool> saveCharacterAsync(entt::registry& registry, int slotIndex);
    bool loadCharacter(entt::registry& registry, int slotIndex);
    
private:
    // Helper to capture state from ECS to DTO
    CharacterSaveData createSnapshot(entt::registry& registry);
    
    // Helper to restore ECS from DTO
    void restoreFromSnapshot(entt::registry& registry, const CharacterSaveData& data);
};
```

### 4.2 存档流程 (Save Flow)
1.  **触发**：用户点击“保存”或触发回城（`SharedContext::requestSave`）。
2.  **快照 (Main Thread)**：
    *   获取 `PlayerEntity`，拷贝 `Position`、`PrimaryStats`、`ActiveSkillsComponent`、`SkillContractRuntimeComponent`、`AstrolabeComponent`、`PlayerCombatHistory` 等，构建 `CharacterSaveData`。
    *   深拷贝 `ItemStorageService` 作为物品快照。
    *   **耗时**：极短，因为只是内存拷贝。
3.  **写入 (Taskflow Thread)**：
    *   将 `CharacterSaveData` 序列化为 JSON 载荷，作为 `ProgressionData` 段写入。
    *   以脏段掩码（角色档为除共享仓库外的全部段）调用 `ItemPersistenceCodec::encode` 生成二进制字节流。
    *   经 `SaveFileAtomic` 写入 `saves/temp/slot_<N>.tmp`，校验文件大小后将原档备份为 `.bak`，再原子重命名为 `saves/slot_<N>.nmd`。
    *   并发保护：保存进行中会拒绝新的角色档保存请求。

### 4.3 加载流程 (Load Flow)
1.  **读取**：优先读取 `saves/slot_<N>.nmd`；若解码失败则回退至同名的 `.bak` 备份。
2.  **校验**：核对文件魔数、物品存储版本、段头表 CRC32 与各段 CRC32；角色档还需核对 `SaveHeader::version`，版本不相等即拒绝加载。
3.  **重建世界 (Main Thread)**：
    *   `registry.clear()` 清空世界并创建 `PlayerEntity`。
    *   应用 `Position`、`PrimaryStats`、技能、技能契约运行时、星盘、战斗历史等组件，并以 `StatsDirty` 标记触发衍生属性重算。
    *   物品由 `ItemPersistenceCodec::decode` 直接灌入 `ItemStorageService`，容器槽位镜像到 `InventoryComponent` 等组件，不再创建物品实体。
    *   共享仓库不被角色档覆盖，加载后保留内存中的当前共享仓库数据。

## 5. 一致性与并发约束

*   **单轨物品存储**：所有物品容器（背包、装备、仓库、传家宝、材料银行）统一经由 `ItemStorageService` 与 `ItemPersistenceCodec` 持久化。
*   **角色档与全局档解耦**：角色档写入除共享仓库外的全部物品段；全局档仅写入共享仓库及其依赖段；加载角色档时不覆盖共享仓库。
*   **保存互斥**：角色档与全局档各自持有进行中标志，重复请求会被拒绝，避免并发写入同一文件。
*   **校验失败即拒绝**：文件头、魔数、版本或 CRC32 任一不符即拒绝加载，不做静默重置。
*   **回退链**：主文件不可用时回退到 `.bak`；仅当目标文件完全不存在时才以空数据初始化。

## 6. 关于性能的备注
对于本游戏规模：
*   **Reflectionless Serialization**: 物品存储采用 POD 结构整块序列化，无需运行时反射；角色数据使用手写的 `to_json/from_json` (nlohmann 宏)。
*   **Binary vs JSON**: 物品数据以二进制 `.nmd` 存储，配合增量段缓存与 CRC32 校验；仅角色进度数据以 JSON 载荷内嵌，兼顾体积、速度与可调试性。
