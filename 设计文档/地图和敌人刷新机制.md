# 2D 暗黑Like Roguelite RPG - 地图与敌人系统设计 V0.1

## 1. 地图生成系统 (Map Generation System)

### 1.1 设计目标

- **高可玩面积**：避免由于随机生成导致的死胡同过多或地形破碎。
- **探索感**：配合战争迷雾，引导玩家探索。
- **一次性体验**：玩家通过传送门离开后，当前地图立即销毁。

### 1.2 核心算法推荐：改进型细胞自动机 (Refined Cellular Automata)

为了满足“障碍物不是主流”且“地图开阔”的需求，传统的 BSP（房间分割）可能过于方正。推荐使用参数调整过的细胞自动机：

1. **初始化**：创建一个巨大的网格（例如 128x128），每个格子有 45% 的几率是墙壁，55% 是地板。
2. **平滑迭代 (Smoothing)**：
   - 遍历每个格子，检查周围 8 个邻居。
   - 如果邻居中墙壁数量 > 4，则该格子变成墙壁；否则变成地板。
   - 重复迭代 4-5 次。这会形成自然的洞穴状地形。
3. **连通性检查 (Connectivity)**：
   - 使用 **泛洪算法 (Flood Fill)** 标记最大的连通区域（Main Room）。
   - 剔除所有不与主区域相连的小空洞（填死它们），确保地图没有到达不了的地方。
4. **边界处理**：强制将地图最外圈设为不可破坏的墙壁。

### 1.3 战争迷雾与小地图 (Fog of War & Minimap)

- **数据层**：使用一个 `std::vector<uint8_t> visibility_grid` 与地图网格一一对应。
  - `0`: **未探索 (Unexplored)** - 全黑，不渲染地形和单位。
  - `1`: **已探索 (Explored)** - 灰色半透明，渲染静态地形，但不更新/渲染动态单位（敌人）。
  - `2`: **当前可见 (Visible)** - 全亮，渲染所有内容。
- **更新逻辑**：
  - 玩家移动时，以玩家为圆心，半径 $R$ 内的格子设为 `Visible`。
  - 上一帧是 `Visible` 但当前不在半径内的，降级为 `Explored`。
- **小地图实现**：
  - 小地图本质上是一个动态生成的纹理 (`Texture`)。
  - 每当 `visibility_grid` 发生大面积改变（或每隔 N 帧），更新小地图纹理的像素数据。
  - UI 上使用圆形遮罩 (Mask) 裁剪显示。

## 2. 敌人生成与管理系统 (Enemy Spawning & Management)

### 2.1 种族与群聚机制 (Races & Clustering)

- **种族池 (Race Deck)**：
  - 定义全局种族库（骷髅、兽人、蜘蛛、恶魔等）。
  - **Map Init**：每张地图生成时，随机抽取 2-4 个种族作为本关卡的“生态系”。例如：本关只有“骷髅”和“蜘蛛”。
- **群聚生成 (Cluster Spawning)**：
  - 不在地图上均匀撒胡椒面，而是基于“据点”生成。
  - 随机选取地图上的空地作为 `ClusterCenter`。
  - 在 `ClusterCenter` 周围半径 $R$ 内生成 5-10 个同种族的敌人。
  - *精英怪逻辑*：每个群聚有 10% 几率包含一只精英怪（颜色不同、体型稍大）。

### 2.2 性能优化：静态数据 + 动态激活 (The "Dormant" System)

解决“全图大量敌人”与“性能”矛盾的核心方案。

#### 阶段一：生成 (Generation Phase)

地图加载时，不创建真正的游戏对象 (GameObject)，只生成数据。

```
struct EnemySpawnData {
    Vector2 position;
    uint16_t enemy_type_id; // 对应种族ID
    uint8_t level;
    bool is_elite;
    bool is_alive = true;   // 玩家杀怪后置为 false
};

// 存放在 MapManager 中
std::vector<EnemySpawnData> all_enemies_on_map;
```

#### 阶段二：运行时 (Runtime Phase)

使用 **空间哈希 (Spatial Hash)** 或 **网格索引** 管理激活状态。

- **激活范围 (Activation Range)**：玩家周围屏幕外扩 10% 的区域。
- **逻辑循环**：
  1. 检测玩家位置。
  2. 查询“激活范围”内的 `EnemySpawnData`。
  3. 如果数据存在且 `is_alive` 为真，且当前没有对应的 `EnemyEntity` 实例 -> **生成实体 (Spawn)**。
  4. 如果某个 `EnemyEntity` 跑出了“卸载范围”（比如玩家走远了） -> **销毁实体 (Despawn)**，但在销毁前将当前血量等状态写回 `EnemySpawnData`。
- **低频行为**：
  - 对于处于“休眠”状态的敌人，完全不进行 AI 计算，或者每秒只进行一次极简的“位置迁移”（模拟怪物游荡），防止玩家背板。

## 3. 资源管理与场景切换 (Resource Management)

### 3.1 内存模型 (RAII)

鉴于 C++20，我们利用 `std::unique_ptr` 和 `Scope` 来管理生命周期。

- **LevelContext (关卡上下文)**：
  - 这是一个包括了 `MapGrid`、`EnemyList`、`LootList` 的大容器。
  - 当玩家点击传送门时：
    1. 触发 `TransitionSequence`。
    2. 销毁当前的 `LevelContext` 指针（触发所有析构函数，自动清理 ECS 中的实体和纹理资源）。
    3. 加载界面（Loading Screen）。
    4. `new LevelContext()` 生成新地图。

### 3.2 垃圾回收策略

- **ECS 清理**：使用 Entt 等库时，切换场景必须调用 `registry.clear()`。
- **纹理池**：怪物和地图的 Texture 资源不应该随关卡销毁（因为下一关可能还用骷髅的贴图）。建议使用 `ResourceManager` 单例管理纹理，只有当显存压力过大时才进行引用计数检查并卸载未使用的纹理。

### 总结

这套系统的核心在于：**不要信任屏幕外的事物**。屏幕外的怪物只是一行数据，只有屏幕内的怪物才是实体。这样你可以轻松实现成千上万的怪物总量，而只支付几十个怪物的 CPU 开销。
