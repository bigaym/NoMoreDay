# 剑修三专精界面打磨设计

> 日期：2026-03-08
> 状态：已确认
> 范围：`剑圣 / 魔剑 / 天剑` 三专精的 Mastery Hub、技能专精树、节点语义、Tooltip 与轻量交互动效

---

## 1. 背景

剑修的三条专精开发已完成基础落地，运行时节点行为、专精树安全性、关键节点测试矩阵、技能 VFX 事件管线都已具备可用基础。当前问题不再是功能缺失，而是界面层的专精辨识度不足：

- `UISkillHub` 仍以统一卡片样式为主，剑圣、魔剑、天剑的身份差异主要依赖文本。
- `UISkillSpecRenderer` 当前视觉主题更偏向技能标签颜色，而非 Mastery 身份语言。
- `UISkillTalentTree` 的 tooltip 信息完整，但层级与语义强调偏功能化，尚未形成“构筑仪式感”。

本轮打磨目标确定为“界面视觉优先”，先建立三专精统一且稳定的视觉系统，再用这套系统承接节点语义与轻量交互反馈。

## 2. 目标与非目标

### 2.1 目标

- 建立剑圣、魔剑、天剑三套稳定的 Mastery 视觉语言。
- 将这套视觉语言一致应用到 `Hub / 专精树背景 / 节点 / 连线 / Tooltip / 交互反馈`。
- 提升节点角色可读性，让 `Keystone / Trigger / Synergy / Transmuter / Passive` 在不阅读全文时也能快速辨识。
- 复用现有运行时语义与 VFX 事件，不额外引入一套 UI 语义状态机。
- 保持拖拽、缩放、分配、重置等既有交互路径不变。

### 2.2 非目标

- 不重做专精树布局算法。
- 不改写 `SkillContract`、`NodeContractData`、天赋分配规则或运行时判定。
- 不将整个战斗特效系统镜像进 UI。
- 不引入高成本后处理或需要额外 RenderGraph Pass 的 UI 演出。

## 3. 三专精视觉基调

### 3.1 剑圣

- 关键词：锐、直、决断。
- 形态语言：细长斜切线、前冲箭形、收束式锋刃高光。
- 主色方向：冷白钢青，辅以少量高亮银白。
- 传达目标：贴身、快斩、精准、处决。

### 3.2 魔剑

- 关键词：噬、蚀、危险。
- 形态语言：破碎甲片、内收式脉冲、克制的侵蚀边缘。
- 主色方向：深赤黑铁，辅以暗金血辉。
- 传达目标：高风险、高收益、吞噬、反制。

### 3.3 天剑

- 关键词：御、阵、天降。
- 形态语言：圆弧法阵、悬浮剑轨、垂直落线、环形展开。
- 主色方向：青金天光，辅以淡云白。
- 传达目标：高位操控、远程压制、秩序、领域掌控。

## 4. 界面系统设计

### 4.1 Mastery Hub

`UISkillHub` 保留现有选择、解锁、等级与调试逻辑，但视觉层改为“共享骨架 + 专精皮肤”：

- 共享骨架：卡片尺寸、按钮逻辑、解锁态/选中态/锁定态行为保持一致。
- 专精皮肤：背景纹样、轮廓切角、主高光、选中动画依 Mastery 切换。
- 激活动效：
  - 剑圣：向前掠光。
  - 魔剑：内收式脉冲。
  - 天剑：环形展开。

该层目标是让玩家在进入面板时，先认出专精身份，再进入技能构筑。

### 4.2 专精树背景

`UISkillSpecRenderer` 的背景从“标签色主题光晕 + 通用网格”调整为“基础暗底 + 专精底纹 + 轻量动态层”：

- 剑圣：斜切流线网格。
- 魔剑：裂隙侵染纹理。
- 天剑：阵图与星轨结构。

动态层只允许缓慢漂移、局部呼吸与弱脉冲，不允许持续闪烁、频繁大面积变亮或遮挡节点。

该阶段是替换式重构，不是叠加式加法：现有通用光晕、网格、粒子层在导入专精主题后应同步减量或下线，避免专精树超过当前可读性噪声上限。

### 4.3 节点系统

节点采用“双层语义”：

- 外层表达 Mastery 身份。
- 内层表达节点角色。

保留现有基于角色的尺寸差异与可点状态，但增加以下规则：

- `Keystone`：应有“核心誓约”感，边框厚、脉冲慢、中心符号明确。
- `Trigger`：应有“机关启动”感，边缘具断续激活信号。
- `Synergy`：应有“共鸣回路”感，副环与连线联动最明显。
- `Transmuter`：应有“形态偏转”感，允许引入副色作为元素提示。
- `Passive`：保持最轻量，不与关键节点争抢视觉注意力。

元素副色只允许出现在节点内环、角标、微型徽记或局部副描边中，不能覆盖 Mastery 主身份色。

### 4.4 连线系统

连线保留 `locked / available / active` 的状态结构，但强调方式改为：

- 可达线：低存在感，仅确保路径可读。
- 已激活线：随专精主题色缓慢流动。
- 共鸣线：当连接 `Synergy` 或关键联动节点时，在中段出现一次轻量共振脉冲。

该规则的目标是让玩家快速读懂 build 路径，而不是单靠点亮节点回忆选择顺序。

### 4.5 Tooltip 与信息层级

`UISkillTalentTree` 的 tooltip 维持现有 contract 信息模型，不重构字段，只升级排版与视觉语义：

- 标题条跟随 Mastery 主色。
- `Role / Scope / Exclusion` 改为徽记化展示，而不是平铺文本。
- 关键语义词高亮：`剑意`、`御剑步`、`触发`、`仅限本技能`、`互斥`。
- 元素转化存在时，仅作为副色或小徽记出现，不覆盖 Mastery 主身份色。

由于当前 tooltip 以纯文本换行为主，关键词高亮应通过小型文本布局辅助层落地，不能依赖简单字符串替换，否则会破坏现有换行与裁剪稳定性。

### 4.6 交互动效

本轮界面动效只允许四类短反馈：

- `hover`：微呼吸或细光扫过。
- `allocate`：节点亮起并向外传导。
- `refund/reset`：反向熄灭或收束。
- `mastery select`：专精身份激活。

所有动效均应短时、克制、可预期，避免 UI 抢夺技能演出层的注意力。

## 5. 实现边界与数据来源

### 5.1 不新增 UI 专用语义状态机

本轮不创建一套新的 UI 构筑状态系统。专精身份、节点角色、互斥、范围声明、元素转化等信息优先复用现有：

- `BladeMasteryService` / `BladeMasteryRegistry`
- `SkillContractRuntimeComponent`
- `NodeContractData`
- `SkillSystem` 已提供的角色掩码、元素与关键事件语义

此外，专精树渲染在进入主题化之前，必须先补齐稳定的 `skill_id -> mastery_id` 解析来源。当前数据文件中已有 `mastery_id`，但树定义与加载路径尚未把该信息明确暴露给渲染层，因此该映射应作为实现前置条件。

### 5.2 Theme Profile 作为唯一视觉映射层

建议新增统一的 UI Theme Profile 抽象，负责：

- Mastery 主色 / 辅色 / 危险色 / 高亮色
- 轮廓形态参数
- 背景底纹样式
- 节点外壳风格
- 动效节奏参数

`UISkillHub`、`UISkillSpecRenderer`、`UISkillTalentTree` 只消费 Theme Profile，不各自手写一套颜色常量与分支。

Theme Profile 初版只覆盖当前实现确实需要的字段，优先保持轻量：主辅色、高亮/危险色、背景纹样、节点外壳样式、连线样式、轻动效节奏。后续演出字段另行增补，不在本轮预埋。

### 5.3 共享节点视觉分类

节点主题化前，应先抽出一套共享的视觉分类来源，用于统一：

- 节点半径
- 节点外壳类型
- hover / click 命中边界
- tooltip 徽记角色映射

这样可以避免 `UISkillSpecRenderer` 与 `UISkillTalentTree` 分别推导节点角色，导致命中框、外观与说明不一致。

### 5.4 与现有 VFX 事件的联动边界

UI 只接入高价值、低噪声事件：

- `BuffEnter`
- `BuffExit`
- `EmpoweredConsume`
- `TriggerProc`
- `KeystoneActivate`

这些事件只用于对齐界面语义与短反馈，不用于在 UI 中完整重播战斗特效。

## 6. 分期方案

### Phase 1：视觉基线

- 补齐 `skill_id -> mastery_id` 映射来源。
- 建立共享 Theme Profile / tooltip chrome / 节点视觉分类辅助层。
- 完成 Mastery Hub 卡片主题化。
- 完成专精树背景主题化。
- 完成节点与连线主题化。

验收目标：不开 tooltip、不点节点，也能快速区分三专精身份。

### Phase 2：信息层升级

- Tooltip 标题条、徽记系统、关键词高亮。
- `Role / Scope / Exclusion / Transmuter` 信息重排。
- 元素副色与 Mastery 主色共存规则落地。

验收目标：节点阅读速度提升，核心规则无需逐字扫描即可理解。

### Phase 3：交互动效打磨

- hover / allocate / refund / mastery select 四类短反馈。
- Keystone / Trigger / Synergy 的差异化点亮反馈。

验收目标：构筑过程有明确的“被激活感”，但不影响操作稳定性。

## 7. 验收标准

- `辨识度`：Hub 与专精树在中远视距下能稳定分辨三专精。
- `可读性`：缩放、拖拽、节点密集区下依然清楚，不因装饰层失真。
- `语义清晰`：`Keystone / Trigger / Synergy / Transmuter / Passive` 可快速识别。
- `一致性`：Hub、树、tooltip、动效遵循同一视觉语言。
- `轻量性能`：缩放、拖拽、批量高亮时无明显卡顿。
- `可扩展性`：后续若接技能预览或微演出，无需推翻 Theme Profile 结构。

## 8. 风险与约束

- 若直接在多个 UI 文件内散落主题逻辑，后续维护会快速退化为重复分支。
- 若元素转化色覆盖 Mastery 主色，会削弱三专精身份感。
- 若沿用现有通用背景/粒子层再叠加新主题，专精树会迅速超过噪声阈值。
- 若交互动效过强，专精树会从构筑工具退化为噪声源。
- 若引入需要新增 RenderGraph Pass 的 UI 演出，将偏离本轮“界面视觉优先”的轻量范围。

## 9. 结论

本轮打磨应被视为一次 `UI 视觉系统重构`，而不是零散美术修补。推荐执行顺序为：

1. 身份建立
2. 信息层级
3. 动效反馈
4. 有节制的 VFX 语义联动

这样可以在不扰动运行时基础与既有交互的前提下，优先解决三专精“看起来不像三条体系”的核心问题。
