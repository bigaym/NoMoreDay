# NoMoreDay 设计流程

## 适用范围

在创建或调整功能、系统、玩法、内容合同、数据格式、架构方案或多步骤 Track 前加载本文件。设计通过后进入计划流程（见 `planning.md`）产出 `*-plan.md`。仅修正已明确的实现缺陷且不改变产品行为时，可直接进入实施流程。

## 设计输入

1. 确认用户目标、已有 Track、相关 `conductor/specs/`、`设计文档/` 和产品约束。
2. 将 `conductor` 中的规格和计划视为当前执行依据；`设计文档/` 是上游设计基线。
3. 涉及技术选型时先读取 `conductor/tech-stack.md`；涉及渲染时同时读取渲染主控规格与进度文档。
4. 先查阅相关记忆和现有实现，避免重启已作出的决策或重复已有能力。

## 设计收敛（`*-design.md` 必须回答）

设计说明至少回答以下问题：

- 要解决的问题、目标用户体验和明确的非目标。
- 行为规则、数据所有权、生命周期和跨系统合同。
- 对现有接口、存档、资产、配置、性能预算和回退路径的影响。
- 可观察的验收标准，以及单元、集成、性能或手测的验证方式。
- 未决问题、风险、依赖和需要用户决策的取舍。

优先复用现有术语、数据结构和系统边界。没有明确兼容需求时，不为假设性的旧行为增加兼容层。

## Track 与产出

1. 先确认工作是否归属现有 Track；不得无理由迁移、改名或重分层活跃内容。
2. 设计产出 `docs/specs/*-design.md`（Track 中对应 `spec.md`）：固化范围、合同、依赖、风险和完成定义。
3. 需要持续追踪的多步骤工作，在 `conductor/tracks/<track-id>/` 保持 `spec.md`、`plan.md`、`index.md` 职责清晰；`spec.md` 即本流程的 `*-design.md`。
4. 新建或改变 Track 导航时，同步更新 `conductor/tracks.md` 和最近的索引。
5. 设计通过后进入计划流程产出 `*-plan.md`；范围变化时先更新本设计，再更新计划与实现。

## 边界

- 不在设计文档中写完整实现代码；代码细节交给计划流程的伪代码与实施阶段。
- 不无理由迁移、改名或重分层活跃内容；术语与层级优先沿用既有约定。
