# NoMoreDay 计划流程

## 适用范围

在设计（`*-design.md` 或 Track `spec.md`）通过后、进入实施前加载本文件。把已批准的设计拆解为可执行、可独立验证的实施计划，产出 `*-plan.md`（Track 中对应 `plan.md`）。仅修正已明确的实现缺陷且不改变产品行为时，可跳过本流程直接进入实施流程。

## 计划输入

1. 先读取对应 `*-design.md`/`spec.md` 的范围、合同、验收标准与风险；没有设计时先回到设计流程。
2. 使用代码图谱确认相关调用链、数据流、影响范围和现有实现，避免重复造轮或推翻已批准决策。
3. 查阅相关记忆，确认是否有相邻 Track 或既有实现可复用。

## `*-plan.md` 内容要求

`*-plan.md` 是实施的引导文档，不是代码仓库。必须包含以下小节：

1. 实施思路/原理：清晰细致地说明每个改动点的实现原理、数据流、所属系统边界和为什么这样做；不写完整实现代码。
2. 伪代码引导：用伪代码或接口草图描述关键逻辑骨架，足以让实施阶段据此落地真实代码；不贴可编译的完整代码块。
3. 原子任务拆分：将工作拆为可独立验证的原子任务，标记依赖与顺序，按 `[ ]`/`[~]`/`[x]` 推进状态。
4. 测试方法：明确受影响的测试层级（unit/integration/performance/functional/manual）、新增或调整的回归测试点，以及对应的构建与 `ctest` 命令。
5. 验证任务完成：列出该任务的完成定义与退出标准（可观察的验收证据、阈值、手测步骤），明确"怎样算完成"。

## 计划纪律

- 只为当前设计范围内的工作做计划；发现设计缺口或合同变更时暂停，先更新 `*-design.md`/`spec.md`，再回到计划。
- 不在 `*-plan.md` 中堆砌完整代码、不提前实现；计划的价值是思路与可验证性，不是代码量。
- 复用既有术语、数据结构、系统边界；没有明确兼容需求时不为假设性旧行为加兼容层。
- 性能、线程、RenderGraph 与回退路径相关的改动，计划中必须标出对应约束与验证方式。
- 主循环和渲染路径的计划必须满足既有分配、线程、RenderGraph 与回退约束。

## 与 Track 的关系

- 已立项 Track：`plan.md` 即本流程的 `*-plan.md`（存放于 `docs/plans/`），并在其中维护"测试方法"与"验证任务完成"小节；既有 `validation.md` 可作为历史证据保留，新验证内容直接写入 `plan.md`。
- 独立小任务：可直接在 `docs/plans/` 产出 `<task>-plan.md`。
- 新建或改变 Track 导航时，同步更新 `conductor/tracks.md` 和最近的索引。
- 范围变化时先更新设计，再更新计划，最后进入实施流程（见 `implementation.md`）。
