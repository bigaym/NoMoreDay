# NoMoreDay 审查流程

## 适用范围

在对一个实现包、Track 阶段或 bug 修复做最终实施评审前加载本文件。审查独立于设计与计划流程（见 `design.md`、`planning.md`、`implementation.md`），只判定结果可否提交或必须修改；不为 worker 代理定义实现任务，也不复述上述流程的检查清单。设计评审、计划评审、实施检查等评审文档统一存放于 `docs/reviews/`。

代码与性能硬规则由 `conductor/code_standard.md`（V2.1）承载，本文件在硬否决条款中按章节引用，不在此重述其全文。技术约束以 `conductor/tech-stack.md` 为准。本文件只约束审查报告的产物形状与审查流程，不依赖任何其他审查会话、代理会话、记忆条目或对话上下文，每次审查自包含、与会话无关。

结论用语固定为 `提交` 与 `修改` 两种。

## 何时需要

1. 任何最终实施评审前必加载。
2. 任何评审者在 `docs/reviews/` 写入或更新报告前必加载。
3. 已完成任务对照设计规格与实施计划检查时必加载。
4. 判定结果是否可提交或必须修改时必加载。

## 必要输入

1. 当前 `git status --short` 输出。
2. 设计参考：`conductor/specs/`、`docs/specs/` 或 `设计文档/` 的文件路径或粘贴片段。
3. 实施计划参考：`docs/plans/` 的文件路径或粘贴片段。
4. 已完成的任务、包或阶段名称；若归属某 Track，给出 Track 标识（见 `conductor/tracks.md`）。
5. 本次审查轮次的变更文件清单。
6. 验证命令与观测结果（若有）。构建/测试/lint 输出体量大时重定向到日志文件再引用，禁止把整段原始输出塞进报告。
7. 已知的越界范围、禁用消费者、权限边界及适用的技术栈约束。

## 审查流程

1. 先运行 `git status --short`，记录变更文件边界。
2. 阅读相关设计规格，确认批准的范围、约束、权限、非目标、风险，以及涉及的 `conductor/code_standard.md` 章节。
3. 阅读相关实施计划，确认包目标、触及的权限、首个消费者、禁用消费者、执行步骤与验证证据。
4. 直接检视变更代码与文档。源码优先用 `codebase-memory-mcp` 图谱工具查调用链、数据流与影响范围；配置、脚本、文本或图谱覆盖不到处退回 `grep`/`glob`/`read`（依 `AGENTS.md` 智能体操作规范）。
5. 将实现行为与设计和计划对照，不单凭上报的测试通过判定。
6. 检查变更文件是否造成未声明的权限触及、禁用消费者、存档/数据迁移、大范围重构或工作流/文档漂移。
7. 在变更上下文内评估代码质量、可维护性、安全性、数据丢失风险、确定性风险、错误处理与测试覆盖，对照 NoMoreDay 性能约束（C++20、EnTT、Raylib、Taskflow、OpenGL 4.3 Compute、mimalloc、xsimd，见 `conductor/tech-stack.md`）。
8. 按严重度归类发现项，给出 `提交` 或 `修改` 结论。

## 判定规则

1. 仅当不存在可能使包目标、权限边界、数据完整性、安全性、确定性、NoMoreDay 性能/DOD/ECS 安全约束或必要验证证据失效的问题时，才得 `提交`。
2. 当残留任何阻塞项、高风险缺陷、范围泄漏、缺失的必备行为或未验证的关键路径时，得 `修改`。
3. 仅风格偏好不构成阻塞，除非其造成可维护性或正确性风险。风格细则见 `conductor/code_styleguides/`。
4. 接受的剩余风险必须显式记录，不得隐藏在通过结论里。
5. 必要输入缺失时得 `修改`，并以缺失的证据作为最高严重度发现项。

## 硬否决规则

1. 测试琐碎或为假（如 `REQUIRE(true)` 等无证明覆盖）时得 `修改`。
2. 测试因既有用例被注释、删除、弱化或旁路而通过，且无计划授权时得 `修改`。
3. 变更触及他人权限的文件、状态或内部归属边界时得 `修改`。
4. 变更代码隐藏失败、吞掉必要诊断或伪造验证证据时得 `修改`。
5. 硬否决发现项一律按 `Blocker` 处理，除非设计或实施计划显式授权该行为。
6. 变更引入 UB、Use-After-Free 或内存泄漏（`code_standard.md` §2.2）时得 `修改`。
7. 变更在热路径（Update/Render）或核心玩法逻辑（技能、战斗、AI）中用字符串比较或字符串键做分支，且设计未显式授权时得 `修改`（§7.2 字符串无关核心逻辑）。
8. 变更跨"可能增删组件/创建销毁实体"的操作持有 EnTT 组件指针，且未先把小 POD 拷到栈时得 `修改`（§5.3 EnTT 安全）。
9. 变更使用裸 `new`/`delete` 而非 RAII 容器或智能指针时得 `修改`（§5.2）。
10. 变更使用 `dynamic_cast` 或 C 式转换、且未在低层边界处显式注释理由时得 `修改`（§6.1）。
11. 变更起裸 `std::thread` 而非 Taskflow 图时得 `修改`（§8.1；`tech-stack.md`）。
12. 变更在热路径堆分配或构造字符串临时对象，且无计划授权时得 `修改`（§2.1）。

## 严重度等级

1. `Blocker`：使任务完成无效、破坏必备行为、越界、损坏数据、削弱安全、违反 code_standard 硬规则或妨碍有效验证。
2. `High`：可能的正确性、可维护性、确定性或集成风险，应在提交前修复。
3. `Medium`：有界缺陷、缺失边界用例证明、契约不清或局部可维护性问题，不使整个包失效。
4. `Low`：命名、措辞、局部简化或文档清晰度问题。
5. `Best Practice`：非阻塞的工程改进建议，不影响提交/修改判定。

## 报告生命周期

1. 报告统一存放于 `docs/reviews/`；不得写入 `conductor/reviews/`（该处为历史遗留，不迁移、不重命名、继续只读保留）。
2. 一个被审包/Track/阶段对应一份文件，命名 `YYYY-MM-DD-<topic>-review.md`；示例 `2026-02-10-blade-ascendant-review.md`。
3. 后续审查轮次在同一文件内追加更新。
4. 首次审查建文件并给出发现项与最佳实践建议。
5. 每轮跟进审查追加新的轮次小节：本轮变更内容、复查范围、上一轮发现项中已解决与仍开启的部分。
6. 最终通过审查追加最终结论；不得删除早期轮次。
7. 功能包期间不得改写不相关的历史评审文件。

## 报告必填字段

1. `审查目标`：任务、包、阶段或 bug 修复名称。
2. `结论`：精确为 `提交` 或 `修改`。
3. `审查轮次`：首次审查 / 跟进审查 / 最终通过审查。
4. `输入`：设计路径、实施计划路径、审查标准路径（`docs/workflows/review.md`）与验证证据引用。
5. `变更文件边界`：`git status --short` 摘要与检视过的变更文件。
6. `范围对齐`：设计与计划的对齐评估。
7. `质量与风险评估`：基于代码上下文的发现项，不单凭测试状态；显式标注引用的 `code_standard.md` 章节。
8. `发现项`：按严重度排序的问题，附文件路径与行引用。
9. `最佳实践建议`：针对每个 `修改` 结论给出可执行的工程修复建议。
10. `剩余风险`：通过审查后接受的风险。
11. `下一步动作`：提交 / 修改具体问题 / 补缺失证据。

## 发现项格式

1. 每条发现项以严重度开头。
2. 尽可能附文件路径与行引用（用 `path:line` 形式，如 `src/game/systems/world/PortalSystem.cpp:72`）。
3. 陈述观测到的问题。
4. 说明相对设计、计划、`code_standard.md` 或 `tech-stack.md` 为何成问题。
5. 基于工程最佳实践与 NoMoreDay DOD/ECS 架构给出修复建议。
6. 禁止无法操作的含糊发现项。

## 禁止内容

1. 不得仅凭测试输出批准。
2. 不得省略 `git status --short` 证据。
3. 不得隐瞒相对设计或实施计划的偏差。
4. 除非风险足以支撑该严重度，不得把最佳实践建议升级为强制阻塞项。
5. 不得在审查报告里做实现编辑。
6. 不得在审查报告里新建设计范围、实施范围、Track 或路线图条目。
7. 不得批准违反 `code_standard.md` 中 NoMoreDay 性能、DOD 或 ECS 安全硬规则的变更。

## 出口门禁

1. 变更文件边界已记录，审查方算完成。
2. 设计与实施计划对齐已检查，审查方算完成。
3. 变更代码上下文已直接检视，审查方算完成。
4. 结论精确为 `提交` 或 `修改`，审查方算完成。
5. 通过审查须显式列出剩余风险方算完成。
6. 修改审查须按严重度排序并附修复建议方算完成。
